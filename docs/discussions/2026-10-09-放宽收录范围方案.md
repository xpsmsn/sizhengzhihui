# 放宽收录与展示范围 — 技术方案与实施建议

- 日期：2026-10-09
- 状态：讨论稿（待决策）
- 目标：把站点收录范围从"仅思政专项"放宽到"教育 + 主要领导班子 + 高校"，并让范围调整可在后台可视化操作
- 相关文件：`industry/taxonomy.ts`、`industry/sources.json`、`industry/prompts/*`、`packages/backend/src/sources/filters.ts`、`packages/backend/src/publication/*`、`apps/web/app/routes/admin/*`

---

## 一、背景与目标

当前"思政智汇"是一个**窄焦点**站点：只收思政专项（领袖讲话、思政政策、思政育人案例、思政理论），把教育领域的其他内容、领导活动和普通高校新闻都当作噪声压掉了。

现需要放宽到三个新方向：

1. **教育** — 更广义的教育政策、教育改革、教育要闻
2. **主要领导班子** — 中央及教育部领导关于教育/高校的活动与讲话
3. **高校** — 985/211 等重点高校的动态与做法

约束：放宽不能失控。新增内容进来后，仍要由评分自然分层，避免精选被日常新闻稀释。因此方案采用"**放宽点档位、不降精选门槛**"的策略。

---

## 二、现状诊断：范围收窄发生在哪四处

范围收窄不是单点开关，而是四个环节叠加的结果。放宽必须四处同步调整，只改其中一处都不会生效。

| # | 环节 | 文件 | 当前收窄方式 | 放宽需改 |
|---|------|------|-------------|:---:|
| 1 | 信源 | `industry/sources.json` | 22 个信源全为思政网/教育部思政栏目 | ✓ |
| 2 | 收录过滤 | `packages/backend/src/sources/filters.ts` | `admitListing()` 按 URL 前缀白名单 + 噪声词 + 时间窗过滤 | ✓ |
| 3 | 分类体系 | `industry/taxonomy.ts` | 仅 5 类：讲话精神 / 政策文件 / 改革部署 / 育人实践 / 理论视野 | ✓ |
| 4 | LLM 评分 | `industry/prompts/selection-score.md` | 明确把普通高校新闻（招生就业、科研获奖、学科评估、基建后勤、体育赛事）压到 `sig ≤ 2` | ✓ |

补充说明：

- `filters.ts` 的 `admitListing()` 本身是**中性的**（按信源配置过滤），收窄主要来自信源配置和评分提示词，所以 `filters.ts` 大概率**不用改**，只需改信源配置。
- `packages/backend/src/publication/rules.ts` 的 `isPoolEligible()`（进公开池的条件）和 `scope.ts` 的可见性判断是**展示层的硬边界**，放宽范围**不动它们**——放宽的是"进不进评分"，不是"公众可见性规则"。

## 三、问题 1：调整方案（放宽收录与展示）

### 3.1 分三档放宽

按"重要度 / 权重"分三档，避免一次全放开。每档独立控制，可分批上线。

#### 第一档 · 教育政策与改革（新增，中高权重）

| 项 | 内容 |
|----|------|
| 信源 | 教育部各司局（非仅思政司）、中国教育报、中国政府网教育/政策频道、省级教育厅 |
| 分类 | `CATEGORIES` 新增 `education`（教育要闻）；现有 `reform`（改革部署）扩 guide 覆盖整体教育改革 |
| 评分 | 放宽 `policy_release` / `case_practice` 适用面：从"思政政策"扩到"整体教育政策与改革" |
| 建议权重 | 保持现有 `policy_release` 权重（sig 4 / nov 2 / cred 2 / reson 2 / act 0） |

#### 第二档 · 主要领导班子（新增，中权重）

| 项 | 内容 |
|----|------|
| 信源 | 中国政府网"领导人活动"、教育部领导活动栏目 |
| 分类 | 新增 `leadership`（领导活动）；或与现有 `speech`（讲话精神）合并 |
| 评分 | 现有 `leader_speech` 只收"关于思想政治工作、教育的重要讲话"。放宽为"关于教育、高校的主要领导活动与讲话" |
| 建议权重 | 沿用 `leader_speech`（sig 5），但活动类（非讲话）可略降 sig |

#### 第三档 · 高校动态（新增，低权重）

| 项 | 内容 |
|----|------|
| 信源 | 985/211 高校官网新闻、各校思政/学工/宣传部门 |
| 分类 | 新增 `campus`（高校动态） |
| 评分 | **放宽噪声规则**：把"有可借鉴做法的高校新闻"从 `sig ≤ 2` 提到正常评价；仅"活动通稿、表彰通报"仍压住 |
| 建议权重 | 新增类型或复用 `case_practice`，整体偏低，自然沉底 |

### 3.2 关键原则

1. **放宽"点档位"，不降"精选门槛"**：改的是评分权重与噪声规则，不是入选分数线。新增内容按分数自然分层——教育政策/领导讲话得高分进精选，高校日常新闻得低分沉底。
2. **分类 key 上线后不要改**：`CATEGORIES[].key` 会出现在网址（`/all?category=`）和 RSS（`/feed/category/<key>.xml`）里。新增类可以加，已上线的 key 不改。
3. **噪声规则改为"分级"而非"一刀切"**：现在 `selection-score.md` 把所有普通高校新闻一律 `sig ≤ 2`。改为：**有可迁移机制的**正常评分、**纯活动通稿**仍压住。

### 3.3 文件级改动清单

```text
industry/sources.json                     → 加新信源（或后台页面加，见问题 3）
industry/taxonomy.ts
  ├── CATEGORIES                          → 新增 education / leadership / campus（2-3 类）
  ├── CATEGORY_TAGS                       → 扩充分类标签
  ├── TOPIC_TAGS                          → 补充教育相关主题
  └── ENTITY_TAGS / ENTITIES              → 按需补充教育机构
industry/prompts/
  ├── content-understanding.md            → itemType 七类与标签白名单同步扩充
  └── selection-score.md                  → 类型权重表 + 噪声规则按档位放宽
packages/backend/src/sources/filters.ts   → 一般不动（收窄来自信源配置，非本文件）
packages/backend/src/publication/rules.ts → 不动（展示层硬边界）
```

> 注意：`taxonomy.ts` 与 `prompts/content-understanding.md`、`prompts/selection-score.md` 有强耦合——改了分类标签，必须同步改提示词里的白名单，否则模型会打出不在词表里的标签被系统丢弃。三者要一起改。

## 四、问题 2：数据更新机制（重新抓取 vs 系统自行更新）

### 4.1 结论

**不需要重新抓取原文，只需对存量文章"重新评估"。**

### 4.2 依据：系统数据是分层的

| 层 | 存储 | 性质 | 改规则后 |
|----|------|------|---------|
| 原文正文 | `articles` | **原始数据**（抓一次就固定） | 不用重抓 |
| AI 判断 | `analyses`（itemType / tags / category / score / selected） | **派生数据** | 需重算 |
| 公开投影 | `publications` | **派生数据** | 随 analyses 重建 |

`packages/backend/src/editorial/analyze.ts` 中每条分析都记录了 `prompt_version`。改了提示词 → 版本号变化 → 该文章需要重跑，而原文已经躺在库里，不用再抓。

### 4.3 操作对照表

| 你改了什么 | 需要做什么 | 是否重抓原文 |
|-----------|-----------|:---:|
| 新增信源 | 什么都不用做，worker 自动抓新源 | 否 |
| 改分类 / 标签 / 评分提示词 | **批量重新评估**存量文章 | **否** |
| 改正文抽取规则 | 批量重新抽取正文 | 否（重新取页面） |
| 改信源 URL 前缀 / 噪声词 | 只影响之后的新抓取 | 否 |

### 4.4 实现逻辑

系统**已有单条重评估**能力：

- 后台内容诊断页的"重新评估"按钮 → `POST /api/admin/content/:id/rerun`，`step=analyze`
- 实现位置：`packages/backend/src/admin/content.ts` 的 `rerun()`

**缺的是批量入口**。建议新增：

1. **批量重评估任务**：按 `信源 / 时间范围 / 当前 prompt_version` 筛选存量文章，批量入队重跑 `analyze`
2. 一次点击让全站按新规则刷新，不碰原文
3. 完成后自动重建 `publications`

**建议执行顺序**：

```
改提示词 → 对受影响范围批量重评估 → 观察精选质量 → 不满意再微调档位 → 再重评估
```

> 成本提示：改一次规则约等于重跑一遍分析（有模型调用成本）。注意 `admin/settings` 里的"付费请求上限"，必要时先在小范围样本上试跑（后台已有选样评测 `selectbench` 能力可复用）。

## 五、问题 3：前端可视化管理（页面直接调整展示内容）

### 5.1 现状

后台已有三个管理页面，但都**不涉及"展示内容配置"**：

| 页面 | 文件 | 能力 |
|------|------|------|
| 信源管理 | `apps/web/app/routes/admin/sources.tsx` | 信源增删改、暂停、改采集配置（**已支持，无需重启**） |
| 内容诊断 | `apps/web/app/routes/admin/content.tsx` + `content-item.tsx` | 单条内容：下架 / 仅摘要 / 人工修正 / 重新评估 / 重新抽取正文 / 重新归组 |
| 设置 | `apps/web/app/routes/admin/settings.tsx` | 二维码、通知目的地、付费请求上限 |

**缺口**：展示逻辑（首页有哪些模块、每模块显示什么、显示多少条）目前**写死在前端代码**里，改一次要改代码 + 重新构建。

### 5.2 设计思路：新增「站点展示配置」页

核心是**把写死的展示逻辑变成 DB 里的配置**，前端读配置渲染。

**配置存储**：新建 `site_settings` 表（Postgres，JSONB），或复用现有 settings 存储。

**页面分四块**：

#### ① 首页模块配置

- 勾选 / 排序首页模块：近期关注 / 时间轴 / 主题入口 / 日报入口
- 每模块设置显示条数（如近期关注显示 Top 5）
- 存储形态：
  ```json
  { "modules": [
      { "key": "recent-focus", "enabled": true, "order": 1, "limit": 5 },
      { "key": "timeline",     "enabled": true, "order": 2, "limit": 20 }
  ] }
  ```

#### ② 卡片字段配置

- 每条卡片显示哪些字段：来源 / 时间 / 评分 / 标签 / 摘要 / 阅读时长
- 勾选即生效：
  ```json
  { "cardFields": ["source", "time", "score", "tags"] }
  ```

#### ③ 分类与标签管理（对应问题 1）

- 可视化增删 `CATEGORIES` / `TOPIC_TAGS`（目前写死在 `taxonomy.ts`）
- 每个分类可设：显示名、是否进筛选栏、是否进日报分节、是否进 RSS
- **这是"放宽收录范围"最直观的入口**——非技术人员也能加"教育要闻""领导活动""高校动态"类

#### ④ 精选门槛调节

- 一个滑块整体调精选分数线（目前门槛是代码常量）
- 或按分类设不同门槛

### 5.3 技术实现

```
DB:       新建 site_settings 表（key-value + JSONB）
API:      apps/api/src/routes/admin.ts 加 /api/admin/site-settings 读写（带审计）
页面:     apps/web/app/routes/admin/display.tsx（复用现有 admin/ui 组件）
渲染:     各展示页 loader 读配置 → 按配置裁剪模块 / 字段
打通:     分类 / 标签配置需与 taxonomy.ts 打通——把常量改成"代码默认值 + DB 覆盖"
```

**关键设计点**：

- **代码默认值兜底**：DB 无配置时用现有代码默认值，保证不配也能跑。
- **配置与审计**：每次修改写入现有 `audit_log`（后台已有该机制）。
- **生效方式**：读时生效，不重启；配置变更清相关缓存。

### 5.4 范围建议

展示配置页**不必一次做全**。建议先做 ① 首页模块 + ③ 分类标签管理（这两块直接支撑问题 1 的放宽），② 卡片字段和 ④ 门槛调节作为后续迭代。

## 六、落地优先级

| 优先级 | 事项 | 类型 | 工作量 |
|:---:|------|:---:|:---:|
| P0 | 定档：确认三档新增范围的边界（哪些收、哪些仍排除） | 决策 | — |
| P0 | 改 `taxonomy.ts` + `content-understanding.md` + `selection-score.md`，扩分类与评分档位 | 代码 | 小 |
| P1 | 加"批量重评估"入口，让存量数据按新规则刷新 | 代码 | 中 |
| P1 | 信源扩充（后台加或改 `sources.json`） | 配置 | 小 |
| P2 | 做「站点展示配置」页（模块 / 字段 / 分类 / 门槛） | 代码 | 中大 |

**建议路径**：先做 P0（定档 + 改规则）→ 跑一轮批量重评估看效果 → 满意后再做 P2 可视化配置页。规则边界没定就做配置页，等于白做。

## 七、待决策事项

1. **三档的边界**：每档具体收哪些信源、哪些内容仍排除？
2. **是否新增分类**：`education` / `leadership` / `campus` 是各自独立分类，还是并入现有类？
3. **评分权重**：新增内容按现有类型权重复用，还是新增类型？
4. **展示配置页的范围**：先做模块 + 分类，还是一次做全四块？
5. **上线节奏**：一次性全放开，还是分三批灰度观察？

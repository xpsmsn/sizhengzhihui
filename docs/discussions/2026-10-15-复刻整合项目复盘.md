## 二、技术架构

```
apps/       api（Fastify 接口）· web（React Router SSR 站点）· worker（采集/处理/出刊/定时任务）
packages/   backend（引擎：采集·分析·编辑·报告·回执）· contracts（跨端类型）
industry/   分类 / 信源 / 提示词 / 入选门槛   ← 行业 KnowHow 都在这
site/       站名文案、品牌、根目录固定文件、更新日志、模型预设
database/   SQL 迁移
scripts/    运维脚本（迁移、重评估、一次性工具）
docs/       文档
```

- **技术栈**：Node.js 24 · TypeScript 7 · React Router（SSR）· Fastify · PostgreSQL 17 · pg-boss（任务队列）· Tailwind CSS v4 · Docker Compose · npm workspaces。
- **四个服务、一个镜像**：`setup`（只跑迁移，跑完即退）→ `api` / `worker` / `web`（共用镜像 `sizhengzhihui-app`，`depends_on setup: service_completed_successfully`）。
- **无内网数据库容器**：`DATABASE_URL` 指向 NAS 上的 PostgreSQL（`x-backend.environment` 里是**必填插值**，缺失会直接构建失败）。
- **worker** 承载 pg-boss 队列 + 定时任务（采集、评分、归组、出刊、解读生成、通知），`stop_grace_period: 210s` 保证退出时不打断事务。

### 数据流（一句话）

采集 → 正文抽取 → 预筛 → 独立两次评分 → 门槛入选（同条只占一条）→ 事件归组（同事件取最高分代表）→ 三个出口：**精选列表 / 政策解读（≥82 分）/ 周月报汇编**。

## 三、核心机制速览

### 1. 入选与评分
- 门槛按信源分级（T1 60 / T1.5 65 / T2 76），政策解读另设 **82 分**线（`INSIGHT_MIN_SCORE`）。
- 同一标准独立打两次分，避免单次抖动。

### 2. 事件归组
- 不同来源报道的同一件事聚成一个事件（`fact_id`），同事件**只产出一篇**解读/一张卡片，取评分最高的条目当代表。

### 3. 政策解读（insights）——本项目改动最多的一块
- 触发：定时任务 `reports.insights` 每 10 分钟一轮，每轮最多 5 篇。
- 产出八段结构：速览 / 背景 / 要点 / 意义与影响 / 原文金句 / 对辅导员的启示 / 思考题 / 主体标签。
- 版本机制：`INSIGHT_VERSION = promptVersion("insight")`（提示词文件哈希前 10 位）。**改提示词 = 换版本 = 全部旧解读判定为待重建**。
- 材料：主报道（标题+摘要+正文，正文截 6000 字）**+ 同事件其他报道（最多 3 篇、每篇截 2000 字）**。

### 4. 模型选择
- `modelFor(capability)`：后台设置覆盖 → 环境变量 → 预设 → `default`。
- 生产实际使用的解读模型：**`mimo-v2.6-flash`**，且它**会输出思维链**（回执里能看到 `reasoning_tokens`）。

### 5. 回执与计费（理解这个才看得懂后面所有坑）
- 每次模型调用都先过 `paidRequest`：以 **`logical_key`** 去重，key 由 `模型 + 提示词版本 + system/user 哈希 + temperature + maxTokens + extra` 派生。
- 状态机：`pending → received/completed`（**命中即复用，不再真调模型**）/ `failed`（允许新尝试，`attempts += 1`）/ `unknown`。
- 原始响应（含 `finish_reason`、`usage`）全量存在 `receipts.response` 里 —— 这是后来所有排障的**唯一可信证据源**。

## 五、踩过的坑（重点）

### A. 领域不匹配：上游的测试桩对不上本站领域

- **现象**：CI 的 `check` job 里 **41 个后端测试失败**，报错形如
  `Model glm-5.3-flash returned unusable output: [{ "code":"invalid_value", "path":["itemType"], "message":"Invalid option: exp..." }]`，另有 `'retrying' !== 'pass'`、`/og/items/xxx.png` 404、`/api/site/hot still shows the event of the withdrawn item`。
- **根因**：上游测试桩造的是 `itemType:"model_release" / "product_launch"`、`category:"ai-models"`，而本站的 `itemType` 是自有的政策类取值（讲话/政策发布/案例实践/理论研究/评论/工作通知/宣传报道等），且校验无兜底 → 直接抛"unusable output"。
- **解法（进行中）**：逐个把测试桩迁移到本站领域。**未完成**：仍剩 41 个失败，方向待定（继续迁移 / 先合并 PR / 收窄测试范围）。

### B. CI 适配：外部数据库与无内置 db 服务

- **现象**：`docker` job 报 `error while interpolating x-backend.environment.DATABASE_URL: required variable DATABASE_URL is missing a value`。
- **根因**：站点 compose **强依赖外部 PG**，而 CI 需要一个自洽的数据库；同时冒烟脚本还在检查**已经不存在的路由**（如 `/daily/archive`）。
- **解法**：新增 `docker-compose.ci.yml`（补一个临时 PG、关掉采集与模型调用、注入假 key），冒烟脚本对齐本站路由，`.env.example` 去掉已废弃变量。结果：`docker -> success`。

### C. 部署形态：镜像里没有挂载，改代码必须重建

- **现象**：改了脚本/源码，`docker compose restart` 毫无变化。
- **根因**：`docker-compose.yml` **没有 bind mount**，代码是 `COPY . .` 打进镜像的。
- **解法（记牢）**：任何代码/提示词改动 → `scp` 上传 → `docker compose up -d --build`。
- **衍生注意**：
  - `.env` **不能覆盖**（含 `DATABASE_URL`、`ADMIN_PASSWORD` 等）；
  - **禁止 `docker compose down -v`**（会连数据卷一起删）；
  - 本地 Node v22 vs 镜像 Node 24 —— 本机 `typecheck` 通过不等于镜像行为一致。

### D. 政策解读的坑（本项目最集中的一组）

#### D1. 列表页"只有一部分内容"
三层原因叠加，容易误判为 bug：
1. 只收 **82 分以上**；
2. **同事件合并成一篇**（多来源同一件事只出一篇）；
3. 列表 `limit = 30` **且没有翻页**；叠加每 10 分钟只生成 5 篇 → 早期总量天然偏小。

#### D2. 详情页"只有一部分内容"
- **根因**：单篇解读**字段残缺**（半句、空段），而详情页是"**有值才渲染**"——落库残缺，页面就直接少一段，观感像"内容丢了"。
- **解法方向**：不是改渲染，而是**保证落库的是完整内容**（见 D5）。

#### D3. 光"删数据重跑"没用——回执复用让它不可自愈
- **现象**：删掉残缺的 `insights` 行、等定时任务重跑，结果还是同一份残缺内容。
- **根因**：`logical_key` 没变 → 命中 `status='completed'` 的回执 → **直接复用旧响应，不再调模型**；且 `pendingInsights` 只挑"**缺当前版本**解读"的行，旧版本的行**永远不会被重做**。
- **解法**：要让内容真正变化，必须**改变 logical_key** —— 即改 `maxTokens` 或改提示词（换版本号）。

#### D4. 改提示词的隐藏成本：全量重建
- **现象**：只改了一个提示词文件，结果**所有解读都进入待重建**。
- **根因**：`INSIGHT_VERSION` 就是提示词文件哈希，变了 → 全部旧解读版本不匹配。
- **解法（要预告）**：这既是"自动修复存量"的便利，也是**一次全量调用成本**。总量 36 条 ÷ 每轮 5 条 ≈ **7 轮 ≈ 70 分钟**跑完。改提示词前先说清这个代价。

#### D5. 诊断过程本身：一次误判与三次修正
这是最值得记录的一段，因为它演示了"**用证据而不是靠猜**"的价值。

1. **初判为"输出被截断"**（怀疑输出额度 2200 打满）。据此改了：输出额度 2200 → 3600、拒绝"残篇"入库、重试封顶。
2. **用户追问"是不是模型判断有风险所以停了"** → 用回执实测：
   - 全库内容安全拒绝统计 = **0 条**（`contentFilter` / `1301` 从未出现）；
   - 该条回执 `finish_reason = stop`、`status = completed`；
   - 用量 `completion 811`（含思考 414）**远低于上限**；
   - 原始 `content` 是**完整闭合的 JSON**（末尾是 `}`）。
   → **结论翻转：不是安全拦截、也不是额度截断，是模型把句子写断了**（轻量模型写长 JSON 时"随手收尾"）。
3. **修正一：把"完整性判定"从"字段齐全"改为"只拦截断"**。原设计（要点≥3、思考题≥2，缺一即失败）会把"材料本来就短、模型主动少写"也判失败 → 逼模型凑段落（正是我们最怕的过度解读），且材料薄的条目试满 3 次后**彻底不再生成**，重要讲话反而没有解读。
4. **修正二：加"收尾修剪"**。段落结尾停在悬空连接词（`中/的/和/在与为以…`）上时，落库前裁到最后一个句末标点 —— **确定性地保证页面不留半句**，不依赖模型自觉。
5. **修正三：重试排除条件按版本限定**。原来的"试满 3 次就跳过"没带 `promptVersion`，导致换提示词后仍被**旧版本的失败记录**封死；改为按当前版本匹配。

> **方法论沉淀**：① 先拿证据（`receipts.response` / `usage` / `finish_reason` / 直接抓页面），再下结论；② 不要把"质量问题的表象"当成"机制问题的根因"；③ 任何"重试/退回"策略都要想清楚**代价**（烧钱、占名额、可能永远不产出）。

- **原则**：遵守项目现有 Tailwind + 自定义 token 体系，**项目已有的设计语言优先于外部设计规范**。

## 七、经验与原则（可直接复用）

### 产品取向
1. **宁短勿编**：材料薄就少写几段，绝不为凑段落扩写 —— 过度解读的风险远大于"少一段"。
2. **可溯源**：每一句"意义与影响"都要能在给定材料里找到依据；找不到就删。
3. **不做评价与预测**：只陈述"提出/要求/部署了什么"，不写"意义重大/必将/充分说明"这类拔高判断。
4. **金句必须原文真实句子**，拿不准就留空；页面常驻"以原文为准"免责。
5. **短要短得体面**：允许少写，但每段必须写完整 —— 技术上用"收尾修剪"兜底，不让读者看到半句话。

### 工程原则
1. **判据要机制化**：用 `finish_reason` 这类**事实信号**判断成败，而不是用"字数够不够"猜。
2. **回执即账本**：原始响应、用量、状态全留存 —— 排障时它是唯一可信来源，也让"复用/计费"可审计。
3. **改提示词 = 换版本 = 全量重建**，是一次真实成本，动手前先算笔账。
4. **重试要有上限、要按版本作用域**，否则会（a）烧钱占名额，（b）换版本后仍被旧记录封死。
5. **确定性兜底优于模型自觉**：提示词能减少问题，代码要能保证下限。
6. **落库即呈现**：前端"有值才渲染"的页面，必须在写入侧保证内容完整。

### 协作原则
1. 不确定方向：**停 → 搜 → 问 → 确认 → 再动手**。
2. 破坏性操作（删除、整体覆盖、删卷）**先问**，并优先软删除。
3. 生产问题一律**先取证据再看结论**；结论翻转要明确说明"我之前的判断错了"。
